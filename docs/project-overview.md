# Airport Access Map：プロジェクト概要

## 公式情報が分かれていることで起きる問題

空港で交通障害や大雨が発生すると、旅行者は鉄道会社、バス会社、道路管理者、気象機関、空港、自治体のサイトを順番に確認する必要があります。土地勘や日本語の読解力が十分でない利用者ほど確認に時間がかかり、空港スタッフへの問い合わせも増えます。

Airport Access Mapは、これらの情報を空港単位で整理し、地図、交通サマリー、利用目的別の詳細を同じ画面で確認するためのOSSです。

## 開発者の想い

このプロジェクトの出発点は、開発者自身が公共交通機関の乱れに遭遇した経験です。どの交通機関が動いているのか、代替手段はあるのかを知るために、鉄道、バス、道路、空港などのサイトを何度も行き来しました。移動の判断に必要な情報を確認するだけで、多くの時間と労力がかかりました。

これは一人の利用者だけの問題ではありません。交通障害が起きるたびに、多くの利用者が同じ情報を探し、案内窓口への問い合わせや公式サイトへのアクセスも集中します。空港を起点に交通・気象情報を整理し、多言語で届ける共通の仕組みが業界の基盤として整えば、利用者は次の行動を早く判断でき、交通事業者や空港も繰り返しの案内対応とサーバー負荷を抑えやすくなります。

Airport Access Mapは、その完成形を名乗るものではありません。空港、交通事業者、自治体、技術者が、必要な権利処理と運用体制を整えながら、このような基盤を検討するための、公開されたたたき台にしたいと考えています。

## なぜ、画面配信とデータ更新を分けるのか

災害時に同じ交通事業者や空港のサイトへアクセスが集中するのは避けられません。もしこのアプリが、利用者が画面を開くたびに各事業者へデータを取りに行けば、アプリの利用者が増えるほど公式サーバーへのリクエストも増えます。情報を届けるためのサービスが、公式情報の提供元へ追加の負荷をかける設計にはしない、というのが出発点です。

そのため、次の二つを分離しています。

1. **更新処理**：実運用では、利用許諾を確認した情報だけを所定の間隔で取得し、形式・時刻・情報源を検証して静的JSONへ変換する。
2. **旅行者向け画面**：生成済みのHTML、JavaScript、GeoJSONだけを静的ホスティングから読み込む。交通事業者のAPIやWebサーバーへ直接問い合わせない。

この分離には、三つの狙いがあります。

- **アクセス集中を隔離する**：旅行者の閲覧数と、交通事業者への取得回数を切り離す。
- **取得障害を画面障害にしない**：更新に失敗しても、Andon Gateが不正な候補を止め、直前の正常な静的ファイルを維持する。
- **維持費を増やさない**：常時起動するバックエンドや従量課金の地図APIを使わず、静的ホスティングで配信する。

利用者が画面内の公式リンクを自分で開いた場合は、通常のWeb閲覧としてリンク先へ移動します。一方、地図やサマリーを表示するだけでは、交通事業者のサーバーへリクエストを送りません。

## デモで確認できること

1. 空港名または3レターコードで、国内33空港から確認対象を選びます。
2. 鉄道、空港バス、道路、気象を地図と一覧で確認します。
3. 「空港から移動」「空港へ移動」「空港に滞在」を選ぶと、その目的に必要な情報だけを開きます。
4. 交通障害時の架空シナリオでは、状態変化、対象区間、理由、代替候補の見せ方を確認できます。
5. 空港に滞在する場合は、Wi-Fi・充電、休憩・宿泊、自治体支援、旅行者向け窓口を確認できます。

[AllNew.workでデモを開く](https://allnew.work/demo/airport-access/)

## 現在の実装範囲

- 33空港
- 5言語：日本語、英語、簡体字中国語、繁体字中国語、韓国語
- MapLibre GL JSと国土地理院タイル
- OpenStreetMap由来の静的な参考経路
- 1週間分の架空サンプル履歴
- GitHub Pagesで配信できる静的構成
- 公式リンクのallowlistと壊れたデータを止めるAndon Gate

## 公開デモが実データを使わない理由

交通事業者の公開ページを閲覧できることと、その本文や状態を別サイトで継続的に再配信できることは同じではありません。公開リポジトリには、未許諾の運行情報、取得済み本文、実履歴を収録していません。

実データを接続する場合は、データセットごとに次を確認します。

- 明示ライセンスまたは書面許諾
- 取得可能な項目、更新間隔、キャッシュ期間
- 翻訳と派生表示の可否
- 情報が古い、空、不正な場合の表示停止条件
- 緊急時の運用責任者と公式情報への導線

## 導入を検討するときの判断材料

このOSSがそのまま提供するのは、情報統合のUI、空港追加の構造、架空データ、品質ゲートです。実サービス化には、対象地域のデータ利用条件、運用体制、監視、アクセシビリティ検証を追加してください。

向いている用途：

- 空港や自治体による多言語案内のプロトタイプ
- 交通情報を一画面へ統合するUX検証
- 静的配信とフェイルセーフの技術検証
- 新しい空港を小さな追加コストで展開する実証

このまま使用すべきでない用途：

- 現在の運行可否を保証するサービス
- 救助、避難指示、経路案内を代行するシステム
- 許諾のない交通情報を自動取得・再掲載する運用

## 技術構成

```text
公式情報源 / 許諾済みデータ候補
              │  所定間隔の更新処理だけが取得
              ▼
      Andon Gate / Evidence Gate
              │
      BLOCK ──┴── PASS
        │            │
  直前正常版を維持   静的JSON・GeoJSONを生成
                     │
                     ▼
              Static hosting
                     ▲
                     │  静的ファイルを配信
                 旅行者のブラウザ
```

公開デモでは、上図の入力に架空サンプルだけを使用します。実データへ接続する場合も、旅行者のブラウザが参照するのは検証後の静的ファイルであり、取得処理は画面配信から分離します。
